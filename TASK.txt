# Task: Simplify and Refactor the Entire OpenLibrary Scraper

## 1. Main Objective

I want you to refactor the entire project to make it extremely simple, readable, and easy to understand.

The current implementation works, but its architecture is unnecessarily complicated for the actual task.

It contains too many files, too many small functions, excessive abstractions, and unnecessary layers of communication between modules.

**The goal is NOT to build a more sophisticated system. The goal is to build the simplest professional implementation that correctly performs the required task.**

The final code must be understandable and reviewable by a fresh software engineer who is still developing programming experience.

I want to be able to open the project, start from `main.py`, and understand exactly what happens, follow every function call, trace every API request and response, and understand where every result goes.

Prioritize simplicity, readability, and maintainability over architectural complexity.

---

## 2. Strict File Structure

Keep the production Python implementation in a small set of files, grouped into three responsibility-based folders.

Use this structure:

```text
project/
│
├── main.py
├── config/
│   └── settings.py
├── requests_apis/
│   └── requests_handler.py
├── processing/
│   ├── data_processor.py
│   └── storage.py
│
├── .env
├── .env.example
├── requirements.txt
├── README.md
│
├── data/
│   └── input/
│       └── books.xlsx
│
└── data/
    └── output/
```

Responsibilities:

### 1. main.py
The main entry point.

Responsible for:
- Starting the application.
- Loading settings.
- Initializing logging.
- Reading the input.
- Calling the main processing workflow.
- Printing the final execution summary.
- Handling top-level errors.

Keep the execution flow visible and easy to follow.

### 2. config/settings.py
Responsible for:
- Loading environment variables.
- Reading Node4 proxy credentials.
- Constructing the proxy configuration.
- Defining API settings.
- Defining pagination settings.
- Defining matching thresholds.
- Validating required configuration.

Do not create unnecessary configuration classes or abstractions.

### 3. requests_apis/requests_handler.py
Responsible for ALL HTTP communication with Open Library.

This includes:
- Preparing Search API parameters.
- Sending Search API requests.
- Handling pagination-related API requests.
- Retries and timeouts.
- Handling HTTP errors.
- Receiving and validating JSON responses.
- Fetching Work details.
- Fetching Edition pages.

Keep all API-related operations in this file.

I want to clearly see where requests are created, sent, received, and returned.

### 4. processing/data_processor.py
Responsible for the actual data-processing workflow.

This includes:
- Reading the Excel input.
- Validating input records.
- Normalizing titles and authors.
- Building search queries.
- Processing Search API results.
- Matching input books with Open Library Works.
- Calculating match scores.
- Selecting the best Work.
- Selecting the best Edition.
- Building the final metadata records.
- Managing the sequential processing of books.

Avoid splitting these operations into many unnecessary helper modules.

### 5. processing/storage.py
Responsible for:
- Saving final results.
- Updating the checkpoint.
- Resuming interrupted executions.
- Exporting Excel, CSV, and JSON files.
- Creating the execution report.

Keep storage operations straightforward.

**Important:** This is the maximum number of production Python files, not a target that must be filled unnecessarily. If two responsibilities can be combined without making the code harder to read, prefer the simpler solution.

The user explicitly requested removing all test files; do not restore them unless asked.

## 3. Eliminate Unnecessary Complexity

Review the entire existing codebase and identify unnecessary complexity.

Specifically:

### A. Too Many Functions

I do not want a function for every two or three lines of code.

Avoid creating functions that:
- Only return another function's result without adding meaningful value.
- Simply pass parameters to another function.
- Perform a trivial operation used only once.
- Exist only to create additional architectural layers.
- Make the execution flow harder to follow.

Combine related operations when this makes the code easier to understand.

However, do not combine everything into one enormous function.

Create functions when they represent a meaningful operation or make the code easier to read.

### B. Avoid Unnecessary Abstractions

Remove unnecessary:
- Classes.
- Interfaces.
- Service layers.
- Wrapper functions.
- Data-transfer objects.
- Dependency injection structures.
- Complex inheritance.
- Generic frameworks.
- Overengineered error-handling systems.

Use straightforward Python functions, dictionaries, lists, and simple classes only when genuinely necessary.

Do not introduce design patterns just for the sake of using design patterns.

### C. Avoid Unnecessary Data Structures

Do not create multiple representations of the same data unless there is a clear reason.

Prefer simple and understandable data structures.

For example, avoid transforming the same API response through several unnecessary models before it reaches the matching logic.

## 5. Simplify Data Storage

The final results are what matter.

I do NOT need to store the original Excel row data or preserve unnecessary copies of input records.

The application should read the input, process it, and produce the final results.

Simplify persistence as follows:

- Store the final processed results.
- Store only the minimum checkpoint information required for recovery.
- Keep the book identifier and processing status where needed.
- Avoid saving entire input rows.
- Avoid duplicating the same information across multiple files.
- Avoid storing raw API responses unless they are genuinely required for recovery or correctness.

The checkpoint should be simple and understandable.

For example, it should be possible to identify:
- Which books have been processed.
- Which books are still pending.
- Which searches are incomplete.
- Which final results have already been saved.

Do not introduce a complicated storage architecture.

### Data-loss protection

Save results progressively so that an interruption does not destroy already completed work.

Do not mark a book as completed before its final result has been successfully persisted.

The final output must remain consistent with the current implementation.

## 6. Detailed Logging and Execution Tracing

Logging is extremely important.

I want to understand exactly what the program is doing by reading the terminal logs.

The logs must provide a clear execution trace without requiring me to inspect the debugger.

Use Python's standard `logging` module.

Every important operation should produce a meaningful log message.

### A. Application startup

Example:

```text
[INFO] Starting OpenLibrary Scraper
[INFO] Loading configuration
[INFO] Node4 proxy configuration loaded
[INFO] Input file: data/input/books.xlsx
[INFO] Page size: 100
[INFO] Maximum pages: 10
[INFO] Resume enabled: True
```

Never print proxy passwords or credentials.

### B. Input processing

```text
[INFO] Reading input workbook
[INFO] Total valid records: 20
[INFO] Invalid records: 2
[INFO] Starting book 1/20
[INFO] Book title: The Hobbit
[INFO] Author: J.R.R. Tolkien
```

### C. API requests

For every request, show:

```text
[INFO] Sending Search API request
[INFO] Query: title:"The Hobbit" AND author:"J.R.R. Tolkien"
[INFO] Offset: 0
[INFO] Limit: 100
[INFO] Request attempt: 1/3
```

After receiving the response:

```text
[INFO] Search API response received
[INFO] HTTP Status: 200
[INFO] numFound: 250
[INFO] start: 0
[INFO] Documents returned: 100
[INFO] Next offset: 100
```

### D. Pagination

Clearly show:

- Current page.
- Current offset.
- Expected total.
- Documents returned.
- Unique Work IDs.
- Next offset.
- Why pagination continues or stops.
- Whether the search is complete or incomplete.

### E. Matching

For every important candidate, log:

- Work ID.
- Work title.
- Title score.
- Author score.
- Publisher score.
- Year score.
- Language score.
- Final weighted score.
- Matching status.

Then log the selected Work and explain why it was selected or rejected.

### F. Metadata retrieval

Show:
- Selected Work ID.
- Work details request.
- Edition pages requested.
- Number of Editions received.
- Edition matching scores.
- Selected Edition ID.
- Missing metadata fields.
- Final metadata status.

### G. Saving results

Show:
- Result being saved.
- Checkpoint updated.
- Current progress.
- Output files generated.
- Final success or failure.

### Logging requirements

- Use consistent log levels: DEBUG, INFO, WARNING, ERROR.
- Use clear and descriptive messages.
- Include the book ID or index in relevant messages.
- Include the page number and offset for pagination.
- Include exception details when errors occur.
- Avoid vague messages such as "Processing..." or "Something went wrong".
- Do not log the same event repeatedly without a reason.

The log should allow me to trace the complete lifecycle of a single book from input to final output.

I want functions to appear in the same order that they are logically executed.

1. Build request parameters.
2. Send the request.
3. Handle the response.
4. Retrieve all pages.
5. Retrieve Work details.
6. Retrieve Editions.

In `processing/data_processor.py`:

1. Read input.
2. Normalize data.
3. Build search queries.
4. Process Search results.
5. Calculate matching scores.
6. Select the best Work.
7. Retrieve metadata.
8. Build final results.
9. Run the complete processing workflow.

This is an illustrative order. Use the actual dependencies to determine the final order.

Do not place related functions randomly throughout the file.

A function should appear close to the functions it calls or supports.

The reader should be able to follow the file from top to bottom and understand the workflow naturally.
