OPEN LIBRARY SCRAPER
ERROR HANDLING AND EDGE CASES AUDIT
===================================

Audit date: 2026-11-03
Scope: Read-only review of the project source and relevant tests.
Source files were not changed during this audit.


1. EXECUTIVE SUMMARY
--------------------

This audit identified 63 distinct cases, grouped where multiple closely
related conditions follow the same code path:

  Handled:          22
  Partially handled:33
  Not handled:       8
  Total:             63

"Handled" means the source contains an explicit check, conversion, fallback,
or reporting path for the scenario. It does not mean every case has a
dedicated test or that all downstream effects are recovered.
"Partially handled" means some useful behavior exists, but an important
input, response, persistence, or execution edge remains unsafe, ambiguous,
unbounded, or incorrectly reported.
"Not handled" means there is no safe, explicit handling path for the
identified scenario. These labels describe implementation, not business
severity.

The strongest areas are ordinary HTTP request failures, common workbook
validation, structural Search API response parsing, raw JSON read/write error
conversion, and per-file export attempts. The highest-risk gaps are unbounded
Retry-After delays, unchecked checkpoint schemas, output-directory setup
failures, unexpected exceptions outside ScraperError, incorrect success exit
codes for degraded runs, and CSV spreadsheet-formula interpretation.

The audit inspected source and existing tests. It did not contact Open
Library or induce actual filesystem/network failures. Test coverage is
summarized near the end; an implemented branch is not presented as
independently runtime-tested unless an existing test covers it.

3. COMPLETE CASE INVENTORY
--------------------------

Each case states the scenario, the code's actual detection/handling, recovery
and impact, classification, and code location. File paths are relative to the
project root. Line numbers identify the inspected implementation and may
shift after future edits.


3A. INPUT WORKBOOK AND RECORDS
------------------------------

I-01 - Missing or unreadable workbook
  Scenario: The configured input path is missing, is not a file, or the
  workbook cannot be opened because of common I/O, format, ZIP, or value
  errors.
  Detection/current handling: read_books() checks is_file(); load_workbook()
  errors in its explicit exception list are converted to InputValidationError.
  Recovery/impact: No retry or alternate file is attempted. The error reaches
  main(), which prints an error and exits nonzero; no book processing starts.
  Status: HANDLED.
  Location: processing/books.py, read_books(), lines 92-104;
  main.py, main(), lines 39-42.

I-02 - Empty workbook or missing required headers
  Scenario: The active worksheet has no header row, or lacks one or more
  required columns.
  Detection/current handling: StopIteration on the first row becomes
  InputValidationError; missing required column names are enumerated.
  Recovery/impact: The user must correct the workbook. No requests are sent.
  Status: HANDLED.
  Location: processing/books.py, _read_workbook_records(), lines 106-120.

I-03 - Missing title/author, blank targets, invalid year, None, or NaN
  Scenario: A row has no title or author, has blank target metadata, contains
  None/NaN, or has a nonblank invalid target year.
  Detection/current handling: _cell_value() converts floating NaN to None;
  normalization converts None to empty text. Title and author are row-level
  required values. A nonblank target year that does not parse as an integer
  year is an error. Blank year, publisher, language, and subject are allowed.
  Invalid rows remain represented with errors and are skipped for search.
  Recovery/impact: Invalid title/author rows do not search; missing optional
  targets reduce matching/Edition-selection evidence without a warning.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, normalize_source_text(), _cell_value(),
  _year(), _read_workbook_records(), lines 42-48, 69-89, 140-166;
  processing/pipeline.py, SearchPipeline.run(), lines 179-198.

I-04 - Duplicate input rows and duplicate header names
  Scenario: The same normalized row appears more than once, or a header label
  appears multiple times.
  Detection/current handling: Duplicate records are marked invalid and retain
  duplicate_of. Header names are placed in a dictionary; a later duplicate
  header silently replaces the earlier position.
  Recovery/impact: Duplicate rows are skipped during search. Duplicate
  headers can cause values to be read from an unintended column without a
  validation error.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, _read_workbook_records(), lines 114-119,
  149-166.

I-05 - Workbook opens but iteration or cleanup fails
  Scenario: The workbook is damaged or its lazy read raises during row
  iteration, or close() raises.
  Detection/current handling: The try/except wraps load_workbook(), but
  _read_workbook_records() runs outside that try. finally calls close() but
  does not map iteration/close exceptions into InputValidationError.
  Recovery/impact: No local recovery. An ordinary exception can escape
  main()'s ScraperError-only handler and terminate the process with a
  traceback.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, read_books(), lines 92-120;
  _read_workbook_records(), lines 106-173.

I-06 - Extremely long strings and unusual cell value types
  Scenario: Workbook cells contain very long titles/authors or values with
  types beyond expected strings/numbers.
  Detection/current handling: There are no explicit length limits. Most
  values are converted to strings by normalize_source_text(); those strings
  can reach query construction and HTTP parameters.
  Recovery/impact: No early rejection or truncation. Large values can increase
  memory/processing/request size or be rejected by downstream libraries or
  Open Library; unexpected conversion failures are not guaranteed to be
  wrapped.
  Status: NOT HANDLED.
  Location: processing/books.py, normalize_source_text() and
  _read_workbook_records(), lines 42-48, 140-166;
  requests/query_builder.py, build_search_queries(), lines 9-20.

I-07 - Formula cells and uncached formula results
  Scenario: Input cells contain formulas whose cached calculated values are
  missing or stale.
  Detection/current handling: load_workbook(..., data_only=True) reads cached
  results, not formula text; no formula-specific warning or validation exists.
  An unavailable cached value becomes None and follows ordinary blank checks.
  Recovery/impact: User must supply literal values or recalculate/save the
  workbook. Formula-derived input can be absent or stale.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, read_books(), lines 92-104.

I-08 - Replacement characters and Unicode/control characters
  Scenario: Text includes U+FFFD, control characters, non-ASCII characters,
  or characters that Excel cannot store.
  Detection/current handling: U+FFFD is recorded as a validation error and a
  warning; original input is preserved. Unicode normalization is applied for
  text processing. General control characters are not removed from input.
  XLSX output removes characters matched by ILLEGAL_CHARACTERS_RE; CSV/JSON
  retain source text.
  Recovery/impact: XLSX avoids many illegal-character failures; other formats
  may contain control characters. Replacement-character rows are invalid
  under the current reader behavior.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, normalize_source_text() and
  _read_workbook_records(), lines 42-48, 149-166;
  processing/export.py, _excel_safe_dataframe(), lines 13-19.


3B. CONFIGURATION AND ENVIRONMENT
---------------------------------

C-01 - Missing proxy variables or invalid proxy port
  Scenario: A required NODE4 variable is missing/blank, the port is not an
  integer, or its numeric value is outside the configured range.
  Detection/current handling: Missing variable names are reported together;
  port parsing and 1-65535 range are checked.
  Recovery/impact: Correct configuration and rerun. Startup stops before
  network requests.
  Status: HANDLED.
  Location: config/settings.py, load_settings(), lines 60-73;
  _int(), lines 26-35.

C-02 - Invalid boolean, integer, timeout, retry, or page-size setting
  Scenario: Boolean is not true/false, integer is malformed, or value is
  below its configured minimum.
  Detection/current handling: _bool() and _int() raise ConfigurationError.
  Timeout/page settings require at least 1; retries allow 0.
  Recovery/impact: Correct the environment setting. Startup stops instead of
  running with malformed values.
  Status: HANDLED.
  Location: config/settings.py, _bool() and _int(), lines 16-35;
  load_settings(), lines 121-134.

C-03 - Invalid matching thresholds
  Scenario: Thresholds are nonnumeric, outside 0-1, or possible threshold is
  greater than high-confidence threshold; ambiguity delta is outside 0-1.
  Detection/current handling: Conversion errors and range/order checks raise
  ConfigurationError. NaN also fails the ordered range predicates.
  Recovery/impact: Correct configuration; startup stops.
  Status: HANDLED.
  Location: config/settings.py, load_settings(), lines 82-93.

C-04 - Malformed API base URL syntax
  Scenario: urlsplit() itself raises ValueError for malformed URL syntax,
  such as malformed IPv6 notation.
  Detection/current handling: The resulting scheme, netloc, query, and
  fragment are checked, but urlsplit() is not wrapped.
  Recovery/impact: Correct OPENLIBRARY_BASE_URL. The raw ValueError can escape
  main()'s ScraperError handler, yielding a traceback.
  Status: PARTIALLY HANDLED.
  Location: config/settings.py, load_settings(), lines 95-105;
  main.py, main(), lines 39-42.

C-05 - Proxy host syntax
  Scenario: Proxy host/brackets or characters are malformed.
  Detection/current handling: Host is conditionally bracketed if it contains
  a colon, but host syntax is not otherwise validated before constructing the
  proxy URL.
  Recovery/impact: No startup recovery. Malformation may surface later as a
  requests/proxy error for each affected book.
  Status: NOT HANDLED.
  Location: config/settings.py, load_settings(), lines 62-84.

C-06 - Relative paths, missing input, output writability, and unknown log level
  Scenario: Paths are relative, the workbook is missing, output is unwritable,
  or LOG_LEVEL is unknown.
  Detection/current handling: Relative paths are rooted at project root.
  Missing input is checked by read_books(). Unknown log level falls back to
  INFO through getattr(). Output writability is not tested during config load.
  Recovery/impact: Input failure is reported; output setup failure may escape
  before a report can be written. Unknown logging level continues at INFO.
  Status: PARTIALLY HANDLED.
  Location: config/settings.py, load_settings(), lines 110-134;
  main.py, main(), lines 26-28; processing/pipeline.py, run_pipeline(),
  lines 31-34.


3C. SEARCH QUERY CONSTRUCTION
-----------------------------

Q-01 - Escaped query text and title-only fallback construction
  Scenario: Title/author contains quotes or backslashes, or author is blank.
  Detection/current handling: Quotes and backslashes are escaped; a primary
  title-plus-author query and title-only fallback are returned when author is
  present. With no author, only the title query is returned.
  Recovery/impact: Query escaping is a deterministic transformation. Fallback
  execution is governed separately by P-05.
  Status: HANDLED for the implemented quoting/query construction behavior.
  Location: requests/query_builder.py, build_search_queries(), lines 9-20.

Q-02 - Invalid query or Search API parameters
  Scenario: Blank query/title, nonpositive limit, negative offset, or wrong
  argument types passed directly to the query builder.
  Detection/current handling: build_search_queries() and
  prepare_search_params() raise ValueError for their explicit invalid cases.
  Normal workbook validation and settings reduce common paths to these
  guards, but Pipeline catches ScraperError, not ValueError.
  Recovery/impact: Correct arguments. Direct callers or manually built
  Settings can cause an uncaught exception.
  Status: PARTIALLY HANDLED.
  Location: requests/query_builder.py, build_search_queries() and
  prepare_search_params(), lines 9-30;
  processing/pipeline.py, SearchPipeline.run(), lines 205-208, 286.


3D. HTTP AND NETWORK COMMUNICATION
----------------------------------

H-01 - HTTP 407 and non-retryable HTTP errors (including 400/401/403/404/408)
  Scenario: Proxy authentication fails, or the service returns a client error.
  Detection/current handling: HTTP 407 gets an actionable proxy-auth
  SearchError. Other search 4xx become non-retryable SearchError. For details,
  404 has a record-not-found message and other 4xx become non-retryable
  SearchError. HTTP 408 is not specially retried by status code.
  Recovery/impact: Error propagates to pagination or metadata and is reported
  per book. Credentials, endpoint, or record must be corrected; no status-code
  retry is made for 400/401/403/404/408.
  Status: HANDLED as explicit failure reporting; 408 retry policy is not
  transient-aware.
  Location: requests/client.py, search_page(), lines 79-105;
  get_json(), lines 168-202.

H-02 - HTTP 429/5xx and Retry-After
  Scenario: Rate limiting or server failure, with numeric/date Retry-After.
  Detection/current handling: 429 and 5xx retry up to max_retries, then raise
  SearchError. Default exponential backoff is capped, but parsed Retry-After
  is nonnegative without a maximum or finite-number check.
  Recovery/impact: Ordinary responses retry; a huge delay stalls the run and
  values such as infinity can make time.sleep() raise OverflowError, which
  escapes the request exception handler.
  Status: PARTIALLY HANDLED. Priority: HIGH.
  Location: requests/client.py, search_page(), lines 95-102; get_json(),
  lines 190-197; requests/retry.py, retry_after_seconds() and
  backoff_seconds(), lines 8-27.

H-03 - Transport-level timeouts and connection failures
  Scenario: Connect/read timeout, DNS resolution failure, refused/reset
  connection, proxy failure, or another requests.RequestException.
  Detection/current handling: RequestException is caught; retries occur up to
  max_retries. Final timeouts and proxy/connection/other failures are mapped
  to SearchError. Proxy HTTP 407 from exception status/text is also detected.
  Recovery/impact: Bounded retries through the configured proxy, then
  per-book error handling. No direct-connection fallback.
  Status: HANDLED for requests.RequestException subclasses.
  Location: requests/client.py, search_page(), lines 114-153; get_json(),
  lines 213-246.

H-04 - Non-requests exceptions within request processing
  Scenario: Unexpected session/hook behavior, time.sleep() failure, or another
  exception not subclassing requests.RequestException/SearchError.
  Detection/current handling: Client catches SearchError and
  requests.RequestException, not arbitrary exceptions; main() also only
  catches ScraperError.
  Recovery/impact: No guaranteed retry/report; an unexpected exception can
  terminate the run with a traceback.
  Status: PARTIALLY HANDLED. Priority: HIGH for process-boundary containment.
  Location: requests/client.py, search_page() and get_json(), lines 79-153,
  168-246; main.py, main(), lines 39-42.

H-05 - Invalid JSON or empty successful response body
  Scenario: A successful HTTP response contains invalid JSON, no body, or a
  body such as 204 No Content where JSON is expected.
  Detection/current handling: response.json() ValueError becomes SearchError.
  There is no separate empty-body diagnostic or retry for malformed content.
  Recovery/impact: The request fails clearly and flows through the caller's
  error handling; response is not parsed as a successful empty object.
  Status: HANDLED.
  Location: requests/client.py, search_page(), lines 106-112; get_json(),
  lines 204-211.

H-06 - Redirect behavior
  Scenario: API redirects to another endpoint, or a redirect is not followed
  and returns a 3xx response.
  Detection/current handling: Client does not set allow_redirects; Requests'
  normal GET redirect behavior applies. Any final status >=400 is handled,
  but redirect destination/final URL is not explicitly validated. A remaining
  non-error 3xx proceeds to JSON parsing and may become H-05.
  Recovery/impact: Common redirects may be followed by the library; unexpected
  destination/status is not separately diagnosed.
  Status: PARTIALLY HANDLED.
  Location: requests/client.py, search_page() and get_json(), lines 88-112,
  176-211.


3E. SEARCH PAGINATION AND FALLBACK
----------------------------------

P-01 - Missing, changing, or inexact totals; inconsistent response start
  Scenario: numFound is absent/inexact/changes between pages, or response
  start differs from requested offset.
  Detection/current handling: Uncertainty is recorded for missing/inexact or
  changing totals. A start mismatch records an error and stops the query.
  Recovery/impact: Partial results and uncertainty/errors are returned to the
  pipeline and exported. Completeness still depends on response metadata.
  Status: PARTIALLY HANDLED.
  Location: requests/pagination.py, _retrieve_query(), lines 87-130.

P-02 - Zero results, empty/short pages, or no reliable total
  Scenario: Search has no docs, returns a short page, ends before reported
  total, or omits total metadata.
  Detection/current handling: Empty docs with a known unreached total produce
  an error. A short page with absent exactness can complete if no known total
  says more results remain. Missing numFound is recorded as uncertainty, but
  an empty page can complete when no total is available.
  Recovery/impact: Zero-result search reaches fallback; otherwise retrieval
  completeness may be inferred from a short/empty response without an
  independent completeness check.
  Status: PARTIALLY HANDLED.
  Location: requests/pagination.py, _retrieve_query(), lines 104-150.

P-03 - Search page request failure or maximum page limit
  Scenario: Client raises SearchError, or MAX_PAGES is exhausted before the
  API's reported results are retrieved.
  Detection/current handling: Request failure is retained in retrieval errors;
  page-limit exhaustion is an explicit error and uncertainty.
  Recovery/impact: Partial candidates can still be scored; retrieval is not
  marked complete. A later resumed/retried run may request a missing page.
  Status: HANDLED.
  Location: requests/pagination.py, _retrieve_query(), lines 87-96, 150-162;
  retrieve(), lines 198-237.

P-04 - Duplicate Work IDs and records without IDs
  Scenario: Same valid Work ID appears on multiple pages, or results have no
  valid ID.
  Detection/current handling: Keyed works are deduplicated with first result
  retained; anonymous works are appended without deduplication.
  Recovery/impact: Duplicate keyed candidates are suppressed; anonymous
  duplicates may inflate candidate rows/counts.
  Status: PARTIALLY HANDLED.
  Location: requests/pagination.py, _add_work(), lines 164-172.

P-05 - Fallback query is only attempted when primary returns no Works
  Scenario: Primary query returns some Works but is incomplete or has errors,
  or returns zero Works and fallback also finds none.
  Detection/current handling: Pagination tries queries in order and breaks
  after any Works are returned; it only reaches title-only fallback when
  current query has no Works.
  Recovery/impact: Zero-primary-result fallback works. A nonempty partial
  result prevents fallback, so additional possible candidates can be missed.
  Status: PARTIALLY HANDLED.
  Location: requests/pagination.py, retrieve(), lines 174-196.

P-06 - Empty query sequence supplied to PaginationService
  Scenario: A direct caller passes queries=().
  Detection/current handling: retrieve() indexes queries[0] and later queries[-1]
  without validation. build_search_queries() normally returns at least one.
  Recovery/impact: IndexError escapes; no retrieval result or structured
  ScraperError is produced.
  Status: NOT HANDLED.
  Location: requests/pagination.py, retrieve(), lines 174-196.


3F. API RESPONSE PARSING
------------------------

R-01 - Invalid top-level, docs, or Work-document shape
  Scenario: Search response is not an object, docs is missing/not a list, or a
  docs entry is not an object.
  Detection/current handling: parse_search_page()/parse_work() raise
  SearchError for these structural violations.
  Recovery/impact: Pagination catches SearchError and returns an error/partial
  result; the pipeline can continue to the next book.
  Status: HANDLED.
  Location: requests/response_parser.py, parse_work(), lines 60-77;
  parse_search_page(), lines 79-99.

R-02 - Missing or unexpected optional Work fields
  Scenario: Title/authors/publisher/language/subject are absent or have an
  unexpected iterable/value shape; years are invalid.
  Detection/current handling: Missing fields default to empty values;
  normalized_values() accepts strings/iterables and stringifies members;
  invalid years are skipped. A dictionary is iterable and can become key
  strings instead of a field error.
  Recovery/impact: Search continues, but matching signals may be reduced or
  misleading; no field-level warning is emitted.
  Status: PARTIALLY HANDLED.
  Location: requests/response_parser.py, normalized_values() and _years(),
  lines 36-57; parse_work(), lines 66-77.

R-03 - Missing or malformed Work key
  Scenario: Work document lacks a valid /works/OL...W key.
  Detection/current handling: Work is retained with work_id and URL set to
  None; matching scores it low and select_matches filters records with no ID.
  Recovery/impact: It cannot be selected, but may be present in candidate
  output.
  Status: HANDLED.
  Location: requests/response_parser.py, parse_work(), lines 60-77;
  processing/matching.py, score_work() and select_matches(), lines 48-108.

R-04 - Invalid numeric pagination fields
  Scenario: numFound or start is not integer-like, negative, or boolean.
  Detection/current handling: Conversion errors become None; negative integer
  values and booleans are accepted by int(). Pagination consumes them without
  semantic range checks.
  Recovery/impact: Retrieval may stop early, miscompute offsets, or overstate
  completeness.
  Status: PARTIALLY HANDLED.
  Location: requests/response_parser.py, parse_search_page(), lines 86-97;
  requests/pagination.py, _retrieve_query(), lines 104-142.


3G. WORK MATCHING
-----------------

M-01 - No valid Work candidate or no qualifying score
  Scenario: All Works lack valid IDs, or the best valid Work is below the
  configured possible-match threshold.
  Detection/current handling: Selector excludes missing IDs; no remaining
  candidate returns NO_MATCH; a low-confidence best candidate is normally not
  selected.
  Recovery/impact: No Work metadata requests are made for a NO_MATCH result;
  output records the no-match status.
  Status: HANDLED.
  Location: processing/matching.py, score_work() and select_matches(),
  lines 48-108; processing/metadata.py, retrieve(), lines 229-238.

M-02 - Ambiguous low-confidence candidates
  Scenario: Top two valid-ID candidates are within ambiguity_delta, although
  both may be below the possible-match threshold.
  Detection/current handling: select_matches() checks ambiguity before its
  low-confidence rejection and returns the best candidate. Pipeline annotates
  ambiguity and only downgrades HIGH_CONFIDENCE, not LOW_CONFIDENCE.
  Recovery/impact: Metadata may be fetched for an ambiguous low-confidence
  candidate that would otherwise be rejected.
  Status: PARTIALLY HANDLED.
  Location: processing/matching.py, select_matches(), lines 93-108;
  processing/pipeline.py, SearchPipeline.run(), lines 216-246.

M-03 - Missing target evidence reduces scores without a warning
  Scenario: Publisher, language, subject, or year is missing in an otherwise
  valid row.
  Detection/current handling: Those targets are not all required by row
  validation. Scoring uses zero/missing evidence; no explicit reduced-evidence
  warning is attached.
  Recovery/impact: Matching continues with less evidence, so scores and
  confidence are based on fewer signals.
  Status: PARTIALLY HANDLED.
  Location: processing/books.py, _read_workbook_records(), lines 140-166;
  processing/matching.py, score_work(), lines 48-81.

M-04 - Subject is reported but excluded from overall score
  Scenario: Subject is missing or differs while other signals match.
  Detection/current handling: Subject score is included in details/reason but
  is not in WEIGHTS or the overall-score calculation.
  Recovery/impact: This is an explicit design choice; subject cannot change
  selection/status.
  Status: HANDLED as current documented matching behavior.
  Location: processing/matching.py, WEIGHTS and score_work(), lines 28-31,
  48-87.


3H. WORK DETAILS, EDITIONS, AND METADATA
----------------------------------------

D-01 - Selected Work does not contain a valid Work ID
  Scenario: A selected Work cannot be converted to a valid Open Library ID.
  Detection/current handling: Metadata service reports PARTIAL and does not
  issue Work-details or Edition requests; it can build from search fields.
  Recovery/impact: Search-derived fields may be retained, but detailed
  metadata and Work URL may be absent.
  Status: HANDLED.
  Location: processing/metadata.py, extract_work_id(), lines 46-55;
  OpenLibraryMetadataService.retrieve(), lines 229-252.

D-02 - Work-details endpoint request failure or 404
  Scenario: Work details request raises SearchError, including not found,
  proxy, HTTP, or network failure.
  Detection/current handling: Error is recorded as "Work details"; empty
  details are used and Edition retrieval continues.
  Recovery/impact: Search Work fields can still populate the final record;
  metadata status becomes PARTIAL if errors remain.
  Status: HANDLED.
  Location: processing/metadata.py, retrieve(), lines 255-274;
  requests/client.py, get_json(), lines 168-246.

D-03 - Dict-shaped but incomplete/mismatched Work details
  Scenario: API returns an object that is not an error object but lacks
  expected keys or describes another record.
  Detection/current handling: Only non-dict and truthy "error" are rejected;
  expected fields and returned key identity are not checked.
  Recovery/impact: Payload can be accepted as successful and produce sparse or
  misleading metadata, potentially with a COMPLETED status if Editions work.
  Status: PARTIALLY HANDLED.
  Location: processing/metadata.py, _get_work_details(), lines 321-337;
  retrieve(), lines 255-305.

D-04 - Editions request failure or malformed page structure
  Scenario: Request fails, response is not a dict, entries is missing/not a
  list, or list contains non-dict entries.
  Detection/current handling: SearchError is recorded; Edition pagination is
  marked incomplete and stops. Available Work/search data still builds a
  record.
  Recovery/impact: Metadata status is PARTIAL; Work-level fields survive.
  Status: HANDLED.
  Location: processing/metadata.py, _get_editions(), lines 339-376;
  retrieve(), lines 274-305.

D-05 - Edition size/link metadata and termination anomalies
  Scenario: size is invalid/negative, page is empty while links.next exists,
  size is missing, or MAX_PAGES is reached.
  Detection/current handling: Invalid size conversion becomes None. Known
  total not reached at an empty page and page-limit exhaustion produce errors.
  An empty page with unknown size is marked complete even if next link is
  present; negative total may satisfy offset >= total.
  Recovery/impact: Status is PARTIAL only where an error was added; some
  inconsistent Edition pagination can be reported complete.
  Status: PARTIALLY HANDLED.
  Location: processing/metadata.py, _get_editions(), lines 377-410.

D-06 - No Editions or no suitable Edition
  Scenario: No Editions are returned, or none satisfies the available input
  criteria.
  Detection/current handling: Separate NO_EDITION and NO_SUITABLE_EDITION
  statuses are produced. Edition URL stays null; Work metadata is retained.
  Recovery/impact: No additional retry beyond request-level retries and page
  retrieval.
  Status: HANDLED.
  Location: processing/metadata.py, retrieve(), lines 276-305;
  empty_record(), lines 307-318.

D-07 - Edition suitable on only one criterion or invalid Edition key
  Scenario: Edition matches one available criterion but conflicts on others,
  or selected response object has no valid /books/OL...M key.
  Detection/current handling: Suitability is true if any criterion matches.
  A selected Edition's key is not a prerequisite for selection; invalid key
  yields no edition ID/URL while status may still be COMPLETED.
  Recovery/impact: No warning is generated; a mismatching Edition can be
  selected or completion can be reported without a usable Edition URL.
  Status: PARTIALLY HANDLED.
  Location: processing/metadata.py, _edition_rank() and select_edition(),
  lines 150-213; edition_id_from_key(), lines 58-63; retrieve(), lines 276-305.


3I. CHECKPOINT AND RAW-RESPONSE STORAGE
---------------------------------------

S-01 - Checkpoint file missing, unreadable, or invalid JSON
  Scenario: Resume is enabled but file is absent, unreadable, or corrupt JSON.
  Detection/current handling: Missing checkpoint starts a fresh state;
  OSError/JSONDecodeError on an existing checkpoint become OutputError.
  Recovery/impact: Missing state is initialized; corrupt existing state stops
  the run and requires repair or deliberate --fresh.
  Status: HANDLED.
  Location: processing/storage.py, CheckpointStore.initialize(), lines 21-30.

S-02 - Valid JSON with wrong checkpoint top-level schema is overwritten
  Scenario: Checkpoint parses but is not a dict with a dict-valued books field.
  Detection/current handling: The validity condition fails and code creates
  and saves a new run instead of reporting invalid checkpoint content.
  Recovery/impact: Existing resumable state may be silently overwritten.
  Status: NOT HANDLED. Priority: HIGH.
  Location: processing/storage.py, CheckpointStore.initialize(), lines 21-36.

S-03 - Malformed nested checkpoint state
  Scenario: Top-level books is a dict, but run_id, book entries, query/page
  containers, or expected nested keys are absent or wrong types.
  Detection/current handling: Nested schema is not validated. Later direct
  indexing/iteration may raise KeyError or TypeError.
  Recovery/impact: Resume may crash or consume invalid state instead of
  reporting a clear checkpoint error.
  Status: NOT HANDLED. Priority: HIGH.
  Location: processing/storage.py, initialize(), lines 21-36, run_id(),
  lines 35-37; requests/pagination.py, _get_page(), lines 52-70.

S-04 - Raw response missing, corrupt, unreadable, or unwritable
  Scenario: Optional cached raw file is absent; present file is invalid JSON
  or non-object; permission/disk-full/I/O failure occurs during read/write.
  Detection/current handling: Optional absent files return None and are fetched
  again. Present corrupt files raise OutputError; raw read/write OSError and
  JSON errors are wrapped. A present corrupt cache is not deleted/refetched.
  Recovery/impact: Missing cache has normal request fallback; corrupt cache
  or storage failure propagates and can be mislabeled by the pipeline.
  Status: HANDLED at storage boundary; recovery from corrupt cache is absent.
  Location: processing/storage.py, load_page(), lines 80-93;
  _load_optional_json(), lines 143-155; _write_json(), lines 157-165;
  processing/pipeline.py, SearchPipeline.run(), lines 286-300.

S-05 - Concurrent or interrupted writes
  Scenario: Two processes write the same checkpoint/raw path or process stops
  between temporary write and replace.
  Detection/current handling: Temporary file plus replace is used, but there
  is no lock, unique temp name, fsync, or stale-temp recovery.
  Recovery/impact: No collision protection; concurrent invocations can race,
  and interruption can leave temp files or lose latest progress.
  Status: PARTIALLY HANDLED.
  Location: processing/storage.py, CheckpointStore.save(), lines 43-52;
  RawResponseStore._write_json(), lines 157-165.

S-06 - Resume with a changed input workbook
  Scenario: Workbook contents/order change while reusing the same output
  checkpoint.
  Detection/current handling: No workbook fingerprint or source identity is
  stored/compared; IDs are generated from current row order and cache scope
  includes run/book/query.
  Recovery/impact: User can use --fresh, but no automatic mismatch warning is
  issued. Old checkpoint/cache state can remain associated with new rows.
  Status: PARTIALLY HANDLED.
  Location: processing/storage.py, CheckpointStore.initialize(), lines 21-36;
  processing/books.py, _read_workbook_records(), lines 149-166;
  requests/pagination.py, _get_page(), lines 52-70.


3J. OUTPUTS AND EXPORTS
-----------------------

E-01 - Output directory cannot be created or accessed
  Scenario: Output path is unwritable, invalid, or is a file rather than a
  directory.
  Detection/current handling: mkdir() occurs before surrounding write-error
  handlers in both pipeline setup and export.
  Recovery/impact: OSError can escape as an ordinary exception; main() does
  not catch it, and an execution report cannot be written.
  Status: NOT HANDLED. Priority: HIGH.
  Location: processing/pipeline.py, run_pipeline(), lines 31-34;
  processing/export.py, export_results(), lines 22-29.

E-02 - Individual CSV/XLSX/JSON write failure
  Scenario: Workbook is locked, disk is full, permission is denied, or
  serialization/filesystem failure occurs during output.
  Detection/current handling: Final-books/report JSON writes catch selected
  OSError/ValueError/ImportError and raise OutputError. Tabular exports are
  attempted separately; selected exception types are collected, report is
  written with output_errors, then OutputError is raised.
  Recovery/impact: Other tabular outputs are still attempted, but successful
  files can remain beside failed/missing files. CLI returns nonzero for
  OutputError.
  Status: PARTIALLY HANDLED.
  Location: processing/export.py, export_results(), lines 37-90;
  main.py, main(), lines 39-42.

E-03 - Illegal characters in XLSX cells
  Scenario: String contains characters rejected by Excel/openpyxl.
  Detection/current handling: XLSX dataframe path removes ILLEGAL_CHARACTERS_RE
  matches; CSV/JSON are not sanitized by that helper.
  Recovery/impact: XLSX can be written without mutating original row/JSON
  data; non-Excel formats retain the text.
  Status: HANDLED for the XLSX-specific illegal-character case.
  Location: processing/export.py, _excel_safe_dataframe(), lines 13-19;
  XLSX export lambdas, lines 48-69.

E-04 - Unexpected export-library exception
  Scenario: pandas/openpyxl/serialization raises an exception outside
  OSError, ValueError, or ImportError.
  Detection/current handling: Such exceptions are not caught by the export
  wrappers.
  Recovery/impact: No guaranteed output_errors entry/report write; exception
  can escape the ScraperError-only CLI boundary.
  Status: PARTIALLY HANDLED.
  Location: processing/export.py, export_results(), lines 37-90;
  main.py, main(), lines 39-42.

E-05 - Partial, stale, or non-atomic tabular output
  Scenario: Process is interrupted during CSV/XLSX write, or export fails
  while an older file with the same name already exists.
  Detection/current handling: JSON outputs use temporary files and replace.
  CSV/XLSX write directly to final paths; failed writes do not remove stale
  outputs.
  Recovery/impact: Old/truncated files may be mistaken for this run's output.
  No rollback or manifest marks each output generation.
  Status: PARTIALLY HANDLED.
  Location: processing/export.py, export_results(), lines 37-90.

E-06 - Spreadsheet formula injection through CSV
  Scenario: User/API text begins with a spreadsheet formula marker and the
  CSV is opened in spreadsheet software.
  Detection/current handling: CSV writers pass cell values to pandas without
  formula-prefix escaping.
  Recovery/impact: Spreadsheet software may interpret text as a formula.
  No protection is applied by the exporter.
  Status: NOT HANDLED. Priority: MEDIUM.
  Location: processing/export.py, export_results(), CSV writers,
  lines 53-58 and 68-69.

E-07 - Execution report JSON cannot be written
  Scenario: execution_report.json write/replace fails after other exports have
  been attempted.
  Detection/current handling: Selected OSError/ValueError/ImportError are
  converted to OutputError; main() catches OutputError and returns 1.
  Recovery/impact: No report fallback or rollback; other outputs/checkpoint
  may represent the run while report is absent or stale.
  Status: PARTIALLY HANDLED.
  Location: processing/export.py, export_results(), lines 73-90;
  processing/pipeline.py, SearchPipeline.run(), lines 368-376;
  main.py, main(), lines 39-42.


3K. EXECUTION, RECOVERY, AND LOGGING
------------------------------------

X-01 - Per-book ScraperError catch conflates processing phases
  Scenario: Search, metadata, storage, or checkpoint operation raises a
  ScraperError inside the per-book try.
  Detection/current handling: Pipeline catches ScraperError, appends an error,
  empty metadata, FAILED_SEARCH status, NO_MATCH row, and failed checkpoint
  state. Persistence/metadata errors can therefore be labeled as search
  errors. A checkpoint save in the exception handler can itself fail.
  Recovery/impact: It continues to later books only if handler bookkeeping
  succeeds; an error there can escape. Earlier search/match results may be
  discarded from final per-book rows.
  Status: PARTIALLY HANDLED.
  Location: processing/pipeline.py, SearchPipeline.run(), lines 179-198,
  286-300; errors.py, lines 1-17.

X-02 - Global infrastructure failure status is not populated
  Scenario: Proxy/service outage affects the run globally.
  Detection/current handling: global_errors is initialized empty and no
  append/population path exists in the inspected pipeline, but it controls
  GLOBAL_INFRASTRUCTURE_FAILURE and NOT_ATTEMPTED reporting.
  Recovery/impact: Widespread proxy errors are likely represented as
  per-book failures/COMPLETED_WITH_ERRORS instead of a global failure.
  Status: NOT HANDLED.
  Location: processing/pipeline.py, SearchPipeline.run(), lines 176,
  303-332, 352-367.

X-03 - Unexpected exception not deriving from ScraperError
  Scenario: ValueError, OverflowError, IndexError, TypeError, or unexpected
  library exception escapes lower-level handling.
  Detection/current handling: main() catches only ScraperError; per-book
  handling also catches only ScraperError.
  Recovery/impact: No controlled user-facing error or structured report;
  process can terminate with traceback.
  Status: PARTIALLY HANDLED. Priority: HIGH.
  Location: main.py, main(), lines 15-42;
  processing/pipeline.py, SearchPipeline.run(), line 286.

X-04 - Degraded report can still produce success exit status
  Scenario: Pipeline returns COMPLETED_WITH_ERRORS, failed books, or
  incomplete searches.
  Detection/current handling: main() prints summary and returns 0 without
  evaluating execution_status/errors.
  Recovery/impact: Automation can treat a degraded run as successful unless
  it separately parses execution_report.json.
  Status: PARTIALLY HANDLED. Priority: HIGH for automation reliability.
  Location: main.py, main(), lines 28-38;
  processing/pipeline.py, report construction, lines 328-355.

X-05 - Logging and diagnostics
  Scenario: Unknown LOG_LEVEL or expected/unexpected runtime errors.
  Detection/current handling: Unknown log level safely falls back to INFO.
  Retries and per-book expected failures log messages. Expected failures are
  generally logged without traceback; unexpected errors are not caught/logged
  by main().
  Recovery/impact: Expected failures are visible but some root causes lack
  stack context; unexpected failures may only show interpreter traceback.
  Status: PARTIALLY HANDLED.
  Location: main.py, main(), lines 26-28, 39-42;
  requests/client.py, lines 135-152, 238-245;
  processing/pipeline.py, lines 286-288.

X-06 - User interruption or hard process termination
  Scenario: Process receives an interrupt or is terminated between API
  requests, checkpoint writes, and final exports.
  Detection/current handling: No explicit signal/interrupt handler exists.
  Pages/checkpoints are saved incrementally; exports occur after book
  processing. An owned HTTP session closes when context unwinds normally.
  Recovery/impact: A later run may resume from persisted state; a hard kill
  can leave temp files and old/partial final outputs. No final report is
  guaranteed.
  Status: PARTIALLY HANDLED.
  Location: processing/pipeline.py, run_pipeline() and SearchPipeline.run(),
  lines 31-69, 163-200, 368-376;
  processing/storage.py, CheckpointStore.save(), lines 43-52;
  requests/client.py, __enter__/__exit__(), lines 68-76.

X-07 - --fresh reset and cleanup behavior
  Scenario: Fresh run starts while prior checkpoint, raw response folders,
  or output files exist.
  Detection/current handling: --fresh is passed to initialize(); it makes a
  new run ID and saves new current checkpoint state. Old run-specific raw
  folders are not deleted; final fixed-name outputs are overwritten only if
  export reaches them.
  Recovery/impact: Fresh run avoids reuse of old current checkpoint, but old
  raw data accumulates. Interruption before export can leave old final outputs
  beside the new checkpoint.
  Status: PARTIALLY HANDLED.
  Location: main.py, argument parsing, lines 16-25;
  processing/pipeline.py, run_pipeline(), lines 31-35;
  processing/storage.py, initialize(), lines 21-36, book_dir(), lines 55-68.


4. RETRY AND RECOVERY BEHAVIOR
------------------------------

HTTP request retries:
  - Search and Work/Edition details requests use max_retries + 1 attempts.
  - HTTP 429 and 5xx are retried; exhaustion becomes SearchError.
  - requests.RequestException subclasses (including requests timeout,
    connection, and proxy exceptions) are retried; final exceptions become
    SearchError with a category-specific message.
  - HTTP 407 is reported as proxy-authentication failure, not retried.
  - Other HTTP 4xx, including status-code 408, are non-retryable.
  - Invalid JSON becomes SearchError and is not retried.
  - Retry-After numeric/date delay is preferred when parseable; it is not
    capped, unlike the default exponential backoff.
  - No direct-network fallback is attempted.

Search recovery:
  - Query pages are cached; cached pages can be parsed on resume.
  - Raw response is written before the checkpoint records the page.
  - Primary query fallback runs only when the primary query produced no Works.
  - Pagination reports uncertainty/errors for several metadata inconsistencies
    and enforces MAX_PAGES.

Metadata recovery:
  - Work-details SearchError becomes a metadata error; Edition retrieval still
    proceeds and search Work data can fill gaps.
  - Edition page SearchError or invalid entries stops Edition pagination and
    returns partial metadata.
  - Work/search-level fallback fields are used if Edition fields are absent.

Storage/export recovery:
  - Missing optional cache files lead to API fetches.
  - Corrupt present cache files cause OutputError; no delete/refetch fallback.
  - JSON outputs use temporary files and replace; checkpoint/raw JSON writes
    wrap common filesystem errors.
  - CSV/XLSX outputs are attempted independently for selected exceptions;
    successful files may remain when another export fails.
  - No rollback/cleanup guarantees a fully atomic set of all outputs.

Run recovery:
  - Per-book ScraperError is intended to isolate failures and continue.
  - Resume uses a checkpoint when enabled and not fresh.
  - There is no explicit interrupt handler, checkpoint schema migration, or
    input-workbook fingerprint check.


5. PER-BOOK ISOLATION AND APPLICATION-LEVEL FAILURE
---------------------------------------------------

Per-book behavior:
  - Invalid rows are represented and skipped without issuing search requests.
  - A ScraperError inside the valid-book processing try is recorded, an empty
    metadata record and NO_MATCH row are appended, and the next book is
    attempted if failure bookkeeping/checkpointing succeeds.
  - Search pagination failures are often contained inside RetrievalResult
    rather than thrown; partial Works can still be scored and reported.
  - Work-details and Editions failures can result in PARTIAL metadata without
    discarding the selected Work.
  - The per-book catch labels all escaped ScraperError as FAILED_SEARCH, even
    if the root phase was storage, metadata, or checkpoint persistence.
  - Unexpected non-ScraperError exceptions are not isolated by that catch.

Application-level behavior:
  - Configuration errors, workbook-level validation errors, output errors
    deriving from ScraperError, and other ScraperError from run_pipeline()
    reach main(), which prints a controlled message and returns 1.
  - Exceptions not deriving from ScraperError can escape with a traceback.
  - A returned report can have errors/incomplete searches while main() returns
    0.
  - Output-directory creation and some library failures can escape before an
    execution report is written.
  - A failed execution-report write is converted to OutputError, but other
    output artifacts/checkpoints can already have been written.

7. PRIORITIZED RECOMMENDATIONS
------------------------------

HIGH PRIORITY
  - H-02: Reject non-finite Retry-After values and cap the delay. Ensure sleep
    failures cannot escape request boundaries.
  - S-02/S-03: Validate checkpoint schema before using it. Do not silently
    overwrite syntactically valid but structurally wrong checkpoints; report
    an actionable OutputError and require an explicit fresh-run decision.
  - E-01: Wrap output-directory setup in OutputError handling and fail before
    processing if the destination cannot be created.
  - X-03: Define narrow top-level boundaries for expected third-party and
    filesystem failures so unexpected conditions produce a controlled
    diagnostic without hiding programming errors.
  - X-04: Return a nonzero process status when report status/errors indicate
    failed or degraded execution, especially for automation.

MEDIUM PRIORITY
  - I-05/C-04/Q-02/H-04/H-06: Wrap workbook iteration and malformed config/query
    validation into the application's error hierarchy; validate inputs at
    public service boundaries, and explicitly validate final redirect
    destinations/statuses if redirects are not always acceptable.
  - P-01/P-02/R-04/D-05: Validate nonnegative totals/offsets and define what
    "complete" means when totals are absent, inexact, or inconsistent.
  - P-04/P-05/P-06: Deduplicate or explicitly exclude anonymous works, define
    fallback policy for incomplete primary results, and reject an empty query
    sequence with a domain-specific error.
  - M-02/M-03: Decide whether ambiguous low-confidence Works may be selected;
    report when required matching evidence is absent.
  - D-03/D-07: Validate Work identity and Edition keys before successful
    completion; review whether one matching Edition criterion is enough when
    other supplied criteria conflict.
  - X-01/X-02: Record failure phase accurately and implement or remove the
    unused global-infrastructure status path.
  - E-02/E-04/E-07: Make output errors robust to expected pandas/openpyxl
    exceptions and ensure report-writing failures are visible even when the
    report itself cannot be produced.
  - E-06: Escape spreadsheet formula markers in CSV outputs when the intended
    consumer may open them in spreadsheet software.
  - ADD-05/ADD-06/S-05/S-06/E-05: Improve interruption, concurrent write,
    stale-output, and changed-input behavior; use a clear run/output manifest.
  - I-08: Decide which control characters should be normalized consistently
    across query, CSV, XLSX, and JSON outputs.

LOWER PRIORITY / PRODUCT POLICY
  - I-03/M-03: Clarify which target columns are truly required and whether
    absent values should warn, invalidate, or remain optional.
  - I-04: Reject duplicate header labels instead of silently choosing the
    last one.
  - I-06: Consider practical input length limits with an explicit validation
    message rather than relying on remote/API limits.
  - I-07: Document that formula cells require recalculated cached values, or
    detect formulas and warn.
  - X-05: Add traceback/exception context to diagnostics where safe, while
    keeping credentials and sensitive proxy data out of logs.

9. FINAL MATURITY ASSESSMENT
---------------------------

The project has a useful baseline of explicit domain errors, request retries,
input checks, pagination uncertainty reporting, per-book handling, caching,
and partial-output reporting. For ordinary expected API failures and common
workbook issues, it generally favors a visible error over silent success.

Error-handling maturity is best assessed as DEVELOPING / MODERATE:
  - Common failures have deliberate handling paths.
  - Several "handled" paths stop at the current layer and are not guaranteed
    to recover the run or preserve all prior results.
  - Checkpoint validation, Retry-After bounds, phase-accurate statuses,
    output initialization, unexpected exceptions, and CLI automation status
    are material reliability gaps.
  - "Complete" search/Edition status depends on API metadata and should not be
    interpreted as independently verified completeness.
